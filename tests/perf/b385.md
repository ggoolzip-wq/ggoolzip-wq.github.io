# b385 automatic-recorder CPU investigation (2026-11-07 KST)

## Reproduction

```bash
# Keep a b384 build outside the worktree, then run each sequentially (not alongside tests).
CHROME=/usr/bin/google-chrome python3 tests/bench_b385_cpu.py --html /path/to/b384.html --modes epic,auto,reward,ocr --out before.json
CHROME=/usr/bin/google-chrome python3 tests/bench_b385_cpu.py --modes epic,auto,reward,ocr --out after.json
# Isolate the actual 4-second VP9 save, rather than conflating it with steady-state capture.
CHROME=/usr/bin/google-chrome python3 tests/bench_b385_cpu.py --modes encode --out encode.json
CHROME=/usr/bin/google-chrome python3 tests/test_b385_cpu.py
CHROME=/usr/bin/google-chrome B384_VIDEO_DIR=/workspace/b385 python3 tests/test_b384_video.py
```

Fixtures: committed `tests/fixtures/b352/beam720.webm`. Each run launches a fresh Chromium; 3-second warmup then 12-second sample. CDP SystemInfo process `cpuTime` sum / monotonic wall time measures **CPU-seconds per wall-second across this browser and its workers**, not whole-machine percentage. Main-thread `Performance.TaskDuration` and V8 profiler samples are separate. Synthetic 720p workload, one sample per scenario; timing/scene differences and profiling overhead apply. No user login or API credentials are used. Raw results and browser/platform details: `b385_results.json`.

`epic`: capture/detection only. `auto`: real OCR and automatic-recorder clocks, direct-video fallback. `reward`: real OCR, character and hard Lucid reward-map context, actual box workers and snapshot stream (`captureStream`), cool-down suppresses clip saving. `ocr`: same reward scenario with epic capture disabled. Reward context is refreshed deterministically, not asserted to be OCR recognition of this synthetic map.

## Root causes and changes

* b384 always ran `canvas.toBlob(image/webp)` at 30fps **even when WebM/VideoFrame was selected**, then discarded every resulting WebP. Native WebCodecs path now creates zero such blobs (legacy fallback unchanged). Epic-only sample: 365 unused blobs / 12s -> 0.
* Use an **owned full-frame 720p canvas** for the VideoFrame ring. A tested zero-copy `VideoFrame(video)` variant was rejected: it pinned the bounded live capture buffer pool and stalled the snapshot stream (5 frames then stale); owned copies pass live regression (27 snapshots, zero fallback reads). Capture uses the full-rate video, not the 10fps analysis snapshot; detection keeps its original source. Thus 1080p main-thread cost is not eliminated, even though total CPU falls.
* Shift NCC copied overlapping patches and recomputed fixed template sums repeatedly. Cache fixed sums and use integral frame sums. Message/meso scans similarly reuse summed-area statistics. All candidate locations and thresholds are unchanged, scores and peak locations agree to <1e-9 in deterministic regressions.
* Repeated `arStart` accumulated timer sets and same-video frame callbacks. Restart now clears old clocks and invalidates callback generations. Regression: 7 clocks -> 7, disconnect -> 0.
* Encoder input VideoFrame clones were not explicitly closed. Close after encode and close encoders on failures; no-source shutdown releases the rolling ring. Correct retention arithmetic and keep pending gate's one-second pre-roll.
* Avoid resetting unchanged name/map canvas dimensions.

## Preserved and limitations

No recognition threshold/candidate reduction, lower capture resolution, frame-rate reduction, crop, or bitrate-policy change. Full-frame 720p / 30fps / -1s,+3s are preserved. Actual capture -> IndexedDB -> WebM decode regression: 1280x720 VP9, 120 frames, 759,457B; legacy playback and item linkage pass. ffprobe independently checks the saved file.

This is primarily a steady-state recording-cost fix, not a claim that OCR is now cheap or that every user's CPU will drop from 100% to a specific number. Actual VP9 save remains a transient CPU burst: baseline 7.22 CPU-sec in 2.069s, after 6.57 CPU-sec in 1.758s (essentially unchanged, content/timing vary). Existing unsupported-browser WebP fallback remains more expensive. Very large inputs still require downscaling. User-machine CPU was not measured.

This is a rescaled synthetic fixture, not a user recording.
